# Test strategy

I validate observable business behavior rather than checking only HTTP 200. A room scenario creates uniquely named data, verifies the exact persisted record, updates several independent fields, rereads, and deletes through the ownership ledger. Booking scenarios create their own room to avoid reserving shared inventory. They extract booking IDs, validate persisted dates and deposit state, verify room filtering and availability, correlate generated messages, and find the same date range in room reporting.

Smoke is intentionally read-only apart from authentication. It covers six checks: reusable session validation, room collection/detail consistency, filtered booking reads, message collection reads, branding contact/location, and service health. The default Maven suite is the complete regression. Dedicated suite files select smoke, regression, contracts and integration by TestNG groups. Counts include individual DataProvider invocations; one workflow may contain many assertions. Scope counts overlap and must not be summed as disjoint tests.

Negative and boundary DataProviders use published annotations: room price 1–999 and permitted room types; booking first name 3–18, last name 3–30, positive room ID, email and phone validation; message phone 11–21, subject 5–100, body 20–2000. Authorized room price boundaries are also persisted and reread. I do not infer undocumented limits. Invalid booking payloads use disposable rooms. No unauthorized destructive request targets a shared record.

Contract tests derive from published schemas and source serializers, with documented read-model adaptations in `schema-provenance.md`. Assertions permit unknown additive properties while retaining required structures and documented field constraints. Gateway errors use their own response formats. The integration workflow verifies booking-generated messages because that interaction is present in source and confirmed by execution.

The public platform can reset or be changed by other users. Tests avoid total-count assertions on shared collections and finish dependent operations within one invocation. A vanished or identity-changed owned room is reported as a possible reset and is not deleted. Real cleanup failures fail the test. No assumption is made about token expiry or revocation: the gateway logout handler does not forward revocation to auth in inspected source.

Failure triage uses sanitized HTTP evidence and source contracts. Categories are framework defect, incorrect expectation, application defect, authentication, data issue, environment reset, rate limit, network/infrastructure, or unconfirmed root cause. A 5xx is not automatically relabeled a reset. Regression preserves application failures; no test retry analyzer or successful-exit override is configured. Parallel validation is contingent on sequential stability, with at most two workers.

Exclusions: global branding mutations, arbitrary message-content updates (not supported), assumed token expiry, load/stress testing, and undocumented endpoints. Booking dates are tested through ISO serialization, persisted values, overlap and reversed ranges. Other malformed-date and nonexistent-room-association behaviors remain candidates for further controlled exploration.
